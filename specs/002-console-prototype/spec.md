# Feature Specification: 002-console-prototype

**Created**: 2026-11-20
**Status**: Specified
**Input**: Предметна область «Система бронювання коворкінгу», варіант 19.

## User Scenarios & Testing
### US1 — Бронювання (P1)
Резидент бронює робоче місце або переговорну. Вільний непорожній інтервал додається до Booking; підтвердження надає імітаційний доступ.
Перевірка: створити два суміжні інтервали; обидва приймаються. Перетин на тому самому місці відхиляється.
### US2 — План простору (P2)
Менеджер змінює опис плану розміщення. Перевірка: порожня назва відхиляється; коректний план замінює попередній.
### US3 — Рахунок і тариф (P2)
Бухгалтер виставляє рахунок підтвердженому бронюванню; до підтвердження отримує відмову. Резидент задає тариф наступного місяця; поточний тариф не змінюється.
### Edge Cases
Порожні атрибути, повторний id, невалідна дата, end <= start, перетин часу, відсутній id, скасоване бронювання, рахунок до підтвердження, повторне підтвердження.
## Requirements
### Functional Requirements
- FR-001: три дійові особи: резидент, менеджер простору, бухгалтер; чотири варіанти використання зі свого рядка таблиці.
- FR-002: бронювання має інтервали id, resident, space, start, end; усі обов'язкові, id незмінний і унікальний. Час ISO local datetime, без часових поясів, точність хвилина.
- FR-003: start < end; напіввідкриті інтервали [start,end) не перетинаються для однакового space. Різні місця можуть мати однаковий час.
- FR-004: дані змінюються лише в DRAFT; CONFIRMED/CANCELLED блокують зміни. DRAFT→CONFIRMED лише з інтервалом; DRAFT/CONFIRMED→CANCELLED. Повторне підтвердження відхиляється.
- FR-005: тариф наступного місяця: BASIC або FLEX; поточний тариф не змінюється. Рахунок імітаційний: 150 грн за годину; без реальних платежів.
### Key Entities
CoworkingMember — абстрактний учасник; Resident, SpaceManager, Accountant — нащадки і реалізації TariffPlan.
Booking — ціле; TimeInterval — частина композиції, не змінюється окремо від Booking. AccessControl — інтерфейс імітації доступу; ConsoleAccessControl — реалізація.
## Success Criteria
- SC-001: усі чотири бізнес-сценарії виконуються й дають пояснення українською.
- SC-002: кожний із 3 акторів бере участь мінімум в одному сценарії; жоден невалідний інтервал не приймається.
## Assumptions
Один навчальний Booking на процес; його інтервали — окремі відвідування в межах бронювання. Авторизація ролей і реальні платежі поза обсягом. Доступ і рахунок імітуються.
## Прототип
Консольний Java-застосунок без зовнішніх залежностей. Повідомлення замінюють доступ, рахунок і збереження; усі чотири сценарії виконуються демонстраційно. README містить команди javac/java.
